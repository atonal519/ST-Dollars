# M2-B：匿名大厅与用户对话闭环

日期：2026-10-02。承接已完成的 M2-A、V1 Design §7/§8.4 和技术顶层设计 M2。

## 本轮范围与实现顺序

1. 房间读取：当前聊天绑定的 Universe → 用户已加入的房间 → 匿名成员与分页消息。普通响应不包含真名、人设、tier、角色所有者映射。
2. 输入与 Continue：发送先在 SQLite 保存 `pending_trigger`，可以修改/删除；只有点“继续”才将选中的 pending 消息原子提交给角色。刷新不丢 pending。已提交消息不能普通撤回。
3. 串行与恢复：同一 Universe 最多一轮生成；请求使用稳定 request ID，重复请求返回原轮结果。生成失败保留已提交消息；新一次继续不重复发送用户输入。重启将未完成轮标为 interrupted，而不重跑模型。
4. 前端：房间栏、大厅、双色头像、消息气泡、待回应标记、发送/继续、历史加载、独立 Primary/Secondary 配置。昵称显示不暴露 account ID；文本只按文本渲染。
5. 生命周期：CHAT_CHANGED、打开面板都重载；每次异步操作绑定聊天/界面 revision，旧回执不能进入新聊天。协议升级至 3，后端不匹配时阻止业务操作。
6. 验证：SQLite 服务测试（隔离、pending、幂等、失败保留、锁、历史）、前端状态及桥接测试、类型检查、构建与本地模拟宿主验收。

## 千千结侦察与后续接入

已读 GitHub main 的 README、`docs/public-api.md`、`src/v3/public-memory-bridge.js`。千千结实现以远端 main 为准，不使用本机旧分支作为接入依据。本机更新尝试遇到连接重置；没有合并或覆盖其界面草稿。

来源：<https://github.com/atonal519/ST-MyriadKnots/blob/main/docs/public-api.md>

- 唯一公共入口：`globalThis.qqj_v3_public_bridge_v1`，schemaVersion=1，只读当前聊天。
- `getStatus()`：身份可读不等于记忆或 CSE 完整。
- `getSnapshot()`：已加载摘要、CSE 和人物资料的深复制，不发请求，不调模型。摘要 checkpoint、人物 revision、来源 floor 和 visibility 要原样保留。
- `readMemory()`：可能读取后端；返回 anchor/coverage，主楼正文仍是最高事实源。
- `getPromptSnapshot()`：新版可选方法，仅是最新已准备材料，不是 Dollars 当前问题的独立召回；旧版本可能不存在。
- `hostChatId/qqjChatId/characterLocator/personaLocator` 共同界定来源身份。任何读取前后发生身份变化都丢弃结果。
- `visibility=private/authorial` 不能直接作为其他人物所知；千千结 entity ID 与 Dollars character/account ID 需要显式映射，不能按显示名永久绑定。

本轮只实现可替换的只读 provider 与设置页连接状态；不自动读取全量记忆、不传给角色、不写回千千结。未安装或关闭千千结时大厅仍可正常运行。

M4 再接 External Story Memory → Event/Knowledge 检索与每角色 Context Pack：先校验来源版本和人物知情边界，再按预算选材。Dollars 消息保留在内部 SQLite，主楼记忆保持千千结所有权。

## 已知边界

M2-B 完成不等于 V1 完成。M3 负责建房/私聊/邀请/进退房；M4 负责外部记忆、Event/Knowledge/Focus Catch-up；M5 负责完整 checkpoint/回退/状态补同步。
本轮锁与 conversation_cycle 是对话请求恢复边界，不冒充完整世界 checkpoint。老消息无 profile snapshot 时仅显示旧账号资料回退；新消息保存发送时 profile。
M2-A 的“Primary 未配置时使用 Secondary”保留为明确可见的兼容行为，设置页提示；正式 V1 必配 Primary。

## 手动验收

- 已初始化聊天打开大厅，只见匿名昵称和头像；刷新后历史与待回应消息都在。
- 连发两条，只保存，不调用模型；修改/删除 pending 后点“继续”，只提交仍在队列里的消息。
- 无 pending 可继续；没人想发言显示自然沉默，不显示成错误。
- 调用失败后原消息仍在；再次继续不重复提交。
- 生成期间切聊天，旧消息不会出现在新聊天；回到原聊天可读取已保存输出。
- 旧后端显示版本不兼容，不能继续操作。同步后端并重启 ST 后刷新验证。

## 可亲自体验的本地 Demo（2026-10-14）

用户确认的范围：直接使用真实 SillyTavern 与配置的模型，不另建模拟网页；仅验收 M2 大厅，不扩 M3–M5。版本 0.0.3，协议保持 3。本节不代表已完成真实模型验收。

### 使用步骤

1. 启动本机酒馆，打开 `http://127.0.0.1:8000`。如果刚更新后端，需重启酒馆；前端刷新页面即可。
2. 可直接导入仓库内的 `docs/demo/Dollars-M2-Demo.character.json`，保留/导入内嵌世界书，打开它的专用测试聊天并选择“多人卡”；也可使用世界书中已有独立人物设定条目的角色卡，建议先选包含 2–3 位人物的小型世界书。当前识别流程主要分析世界书条目，尚未将角色卡自身正文作为独立人物设定抽取；不要用“只有主角卡、没有人物世界书”的素材判断本轮人物识别效果。若演示卡识别为 0，先检查内嵌世界书，不要确认空大厅。
3. 在酒馆扩展菜单打开 Dollars，进入“设置”，填写并分别保存角色模型 Primary 与调度模型 Secondary。地址、模型名、Key 使用用户自己的配置；Key 不需要发到聊天里。当前兼容行为是未配置 Primary 时沿用 Secondary，建议验收时两者都明确配置。
4. 回到“聊天”，选择合适的卡类型，点“识别”，核对人物数量后“确认建立”。识别会真实调用模型，并把确认后的角色、匿名账号和大厅写入插件数据库。
5. 连发两条消息；这时仅保存为待回应，不调用对话模型。可修改或删除待回应消息，再点“继续”。角色可能接话、互相交流，也可能合理沉默。没有新输入时也可继续旁观。
6. 刷新页面，检查历史和待回应消息；切换到另一个测试聊天，检查是否保持独立。初始化和“继续”会真实请求模型并产生相应费用，操作次数由用户决定。

### 怎么判断这个 Demo 是否达到目的

- 交互：看得见发送、修改、删除、继续与回应中的区别，不需要运行脚本才能体验。
- 表达：人物有区分，允许互相接话和沉默；匿名聊天页不直接展示账号背后的角色映射。
- 保存：刷新后已确认保存的消息仍在；每个聊天使用自己的 Universe。它们仍写在同一个本地 Dollars SQLite 文件中，不是单独的演示数据库。
- 边界：当前只有近期聊天和人物摘要，不等同于完整独立 Knowledge、长期连续性或千千结记忆。建房、私聊、邀请、主楼事件同步、完整回退均不作为本轮验收标准。

真实模型效果仍待用户验收；代码托管、服务器位置及运行数据迁移的当前接手状态见 `PROJECT_MEMORY.md`。本节不代表模型 Key 或聊天数据应随代码托管。
